# Project Report: Email Spam Detection Using Machine Learning

## Abstract

This project builds a supervised email spam classifier and compares Multinomial Naive Bayes with Logistic Regression. Messages are parsed from the Apache SpamAssassin Public Mail Corpus, subject and plain-text body are combined, exact normalized-content duplicates are removed, and labels are inherited from the corpus folders. A fixed stratified split is made before fitting TF-IDF; both classifiers use identical training/test examples and vectorizer settings. Metrics and error cases are generated by `src/train_evaluate.py`. The observed local experiment results are reported below.

## 1. Problem and objectives

Spam wastes attention and may carry unwanted content. The task is to classify an email text as spam or ham. Objectives: (1) prepare labeled email data reproducibly; (2) prevent train/test leakage; (3) compare two classical text classifiers fairly; (4) examine precision, recall, F1 and error types; and (5) expose a trained model through a local Streamlit demo.

## 2. Data source and preparation

Source: Apache [SpamAssassin Public Mail Corpus](https://spamassassin.apache.org/old/publiccorpus/readme.html), using `20030228_easy_ham.tar.bz2` and `20030228_spam.tar.bz2`. The corpus documentation gives approximately 2,500 easy ham and 500 spam messages. These are EMAIL messages, not SMS. The script parses each message with Python's email MIME parser; extracts the subject and text/plain body; combines them as one feature string; uses the folder identity as ground-truth label; skips empty or malformed content; and deduplicates exact normalized text with SHA-256. It prints the resulting counts for the actual run.

| Class | Meaning | Count in this run |
|---|---|---:|
| Ham | Legitimate email | 2,473 |
| Spam | Spam email | 482 |
| Total | After parsing and exact deduplication | 2,955 |

Limitations: corpus is historical, curated and imbalanced; `easy_ham` represents easier legitimate mail. Some original messages may include personal or offensive material; keep raw data local and do not redistribute it casually.

## 3. Method

Each message is represented by its subject and body. `train_test_split` reserves 20% with `random_state=42` and stratification. Exact hashes are removed before the split; identical hashes therefore cannot cross partitions. TF-IDF is part of each sklearn Pipeline and is fit only on the training text. The shared vectorizer lowercases, strips accents, removes English stop words, uses 1–2 word n-grams, ignores terms in fewer than 2 documents or in over 98% of documents, and applies sublinear term frequency. Both models receive equivalent feature matrices and the same split.

### Algorithms in simple terms

**TF-IDF:** converts words into numeric weights. Terms common in a particular email but uncommon across all training emails get more influence. It is needed because classifiers operate on numbers. The vocabulary and IDF weights are learned from training data only.

**Multinomial Naive Bayes:** estimates how strongly each word supports each class and combines that evidence. “Naive” means it treats word occurrences as conditionally independent given the class, a simplification that often works well for text. `alpha=1.0` smooths word counts so unseen terms do not produce zero probabilities.

**Logistic Regression:** learns weights for word features and combines them into a linear decision score for spam versus ham. `C=1.0` controls regularization; `liblinear` is used as solver and up to 1,000 iterations are allowed.

## 4. Experimental design and evaluation

The held-out test set is not used to tune hyperparameters. Metrics include accuracy (all predictions correct), spam precision (predicted spam that is spam), spam recall (spam caught), and spam F1 (harmonic balance of precision and recall). Confusion matrix rows are actual `[ham, spam]` and columns predicted `[ham, spam]`. False-positive files contain legitimate messages predicted as spam; false-negative files contain spam predicted as ham.

| Item | Observed value |
|---|---|
| Split seed / test fraction | 42 / 20% |
| Training examples | 2,364 |
| Test examples | 591 (495 ham, 96 spam) |
| Multinomial NB (accuracy / spam precision / spam recall / spam F1) | 0.9239 / 1.0000 / 0.5313 / 0.6939 |
| Logistic Regression (accuracy / spam precision / spam recall / spam F1) | 0.9475 / 1.0000 / 0.6771 / 0.8075 |
| NB confusion matrix (actual rows ham, spam; predicted columns ham, spam) | `[[495, 0], [45, 51]]` |
| Logistic confusion matrix (actual rows ham, spam; predicted columns ham, spam) | `[[495, 0], [31, 65]]` |
| False positive / false negative examples | See `reports/*_errors.csv` |

In this observed split, both models made zero false positives; Logistic Regression had fewer false negatives (31 versus 45) and higher spam recall/F1. It performed better on this particular held-out split. A single split of an old corpus is limited evidence; a model with high accuracy can still miss spam or incorrectly block legitimate mail. Artifacts: `reports/metrics.json`, `reports/model_comparison.csv`, and the PNG charts.

The near-duplicate screening found 1,440 character-TF-IDF cosine pairs at threshold 0.95, of which 541 crossed the train/test boundary; 9 crossing pairs had different labels. Because the screening heuristic can flag boilerplate rather than true copies, pairs were retained. Still, shared templates could inflate these scores. A grouped or time-based independent evaluation is needed before making strong generalization claims.

## 5. Application

`app.py` loads the Logistic Regression pipeline saved with joblib and accepts a subject and body. It rejects blank input, displays a readable class, and handles absent/corrupt model files and prediction errors. It displays no probability because calibration has not been evaluated. A prediction is a model label, not proof that a message is safe.

## 6. Reproduction

On Windows PowerShell: create/activate a venv, `pip install -r requirements.txt`, run `python src\prepare_data.py`, then `python src\train_evaluate.py`, followed by `streamlit run app.py`. For offline acquisition, place the official archives in `data/raw` and run preparation with `--local`. Models, raw data and generated reports are excluded from Git.

## 7. Conclusion and future work

The project provides a reproducible baseline comparison over genuine labeled email. The conclusion about which model performed better must be based on the observed report files after execution. Future work: include hard ham and additional corpora, use time-based or external validation, detect campaign near-duplicates, inspect header features, tune thresholds only on validation data, test calibration, and evaluate on current mail before any practical use.
